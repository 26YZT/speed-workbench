# 产品评估结论（评估阶段）

> 重新评估工作台（AionUi/AionCore）的成熟度，回答两个问题：
> 1. 工作台本身已经很成熟了，是否还有必要接入 blueprint / starter-kit 的约束？
> 2. Multica 对工作台有什么帮助？
>
> 结论均基于源码取证，非推测。

---

## 一、先分清两个词：机制 vs 知识

评估一个项目，要分两层看：

| 层 | 含义 | 工作台（AionCore）的现状 |
|---|---|---|
| **机制** | 「怎么干活」的引擎：多 Agent 并行、任务看板、调度、邮箱、MCP、技能加载 | ✅ **非常成熟** |
| **知识** | 「活该怎么干」的领域规则：产品分几步开发、每步验收什么、架构怎么选 | ❌ **基本空白** |

### 1.1 机制层：AionCore 已经成熟（代码证据）

| 机制 | 证据（源码） |
|---|---|
| 多 Agent 并行 | `aionui-team/work_coordinator`：`BTreeMap<String, SlotState>` 多 slot 独立状态机（Idle/Queued/Starting/Running/Paused/Blocked）+ 因果依赖 |
| 任务看板 | `task_board.rs`：`blocked_by` 依赖、`owner` 认领、状态机、实时广播 |
| 队长/队员 | `types.rs`：`TeammateRole`（Lead/Teammate）+ `TeammateStatus`（Working/Thinking/ToolUse/…） |
| 团队治理 | `team-prompts/governance.rs`：「团队治理优先于助手规则」「Lead-only 工具 teammates 禁用」 |
| 多 Agent 后端 | `aionui-session/adapter.rs`：`BackendAdapter`（Claude Code / Codex / ACP / Antigravity / Aionrs） |
| 调度/崩溃恢复 | `scheduler/`：`TeammateManager`、`crash_recovery`、`dedup` |
| 定时/邮箱/MCP/技能 | `aionui-cron`、`mailbox.rs`、`mcp/`、`skill-runtime` + 20 个内置 skill |

### 1.2 知识层：产品开发知识是空白（代码证据）

| 应有 | 实际 |
|---|---|
| 「从想法到产品」的开发 skill | `builtin-skills/` 21 个全是 Office/PPT/PDF/招聘/PPT 3D，**零「产品/开发/PRD/代码」类** |
| 产品开发 SOP（分几步） | `team-prompts/` 只有通用「队长/队员」角色提示词，**没有 PM/架构师/工程师流水线** |
| 阶段闸门/验收标准 | 全仓无「闸门/是否表/证据包」概念 |
| review 门禁（产出需人验收） | `TaskStatus` 只有 `Pending/InProgress/Completed/Deleted`，**没有 InReview** |
| 需求→架构推导规则 | 无 7 层架构 / 组件选型 / 五要素的任何实现 |

## 二、问题 1：是否还有必要接入 blueprint / starter-kit？

### 结论：有必要，但方式变了——**不是「重写约束系统」，而是「把约束降级成知识注入」**。

理由：

1. **blueprint 和 starter-kit 里「机制」的部分，工作台已经有了，不需要重写。**
   - starter-kit 的「6 阶段」不需要写成新状态机 → 团队看板已有状态机；
   - blueprint 的「组件选型」不需要写新调度 → 只需把选型规则作为文本给 Agent 读。

2. **blueprint 和 starter-kit 里「知识」的部分，工作台是零，必须补。**
   - blueprint 提供的是一份「需求→架构」的知识（五要素、7 层、17 组件决策映射表）；
   - starter-kit 提供的是一份「交付质量」的知识（6 阶段、10 项是否表、证据包、3 份手册）。
   - 这两份知识的体积很小（就是几份 markdown），接入成本 = 做成一个内置 skill，**不是写代码**。

3. **判断标准很简单**：如果工作台的 `builtin-skills` 里已经有「产品开发」类 skill，那 blueprint/starter-kit 才真的多余。但取证结果是它一个都没有——全是 Office 文档技能。

### 一句话：工作台是一台「通用 AI 工作台」，不是「产品工厂」。引擎是现成的，但「产品开发该怎么做」这门手艺是空白，blueprint + starter-kit 恰好是这门手艺的教材。

## 三、问题 2：Multica 对工作台有什么帮助？

### 结论：Multica 不帮工作台「造引擎」（引擎工作台已有），而是帮它补「生产级多 Agent 开发」的 4 个短板，按优先级：

| 优先级 | Multica 的能力 | 工作台现状 | 为什么重要 |
|---|---|---|---|
| ⭐⭐⭐ | **Review 门禁**：产出落 review 列，人确认才 ship | `TaskStatus` 缺 `InReview`，Agent 干完直接 `Completed` | 产品工厂最核心的品质保证，防 Agent 糊弄 |
| ⭐⭐⭐ | **隔离 worktree**：每任务独立目录/分支，多 Agent 不冲突 | `aionui-project` 只做「绑定文件夹」，无每任务隔离 | 多 Agent 并行开发同一项目时是硬需求 |
| ⭐⭐ | **准入决策建模** `dispatch.ReasonCode`：稳定枚举「为什么现在不能跑」（runtime_offline/quota_exceeded…） | `work_coordinator` 有 WorkPriority，但无完整拒绝原因建模 | 用户看到「为什么卡住」而不是干等 |
| ⭐⭐ | **用量/成本追踪**：每任务记 token/成本并聚合 | 未看到对应层 | 产品工厂要算每个原型的成本 |
| ⭐ | **26 种 provider 统一契约**（协议族 vs 内置 runtime 两级路由） | `BackendAdapter` 设计类似，但后端更少 | 扩展更多 Agent 后端时的参照 |

### 关键判断：Multica 是「大型项目多 Agent 开发的参考答案」，不是「要装进工作台的代码」。要借鉴的是它的 4 个设计思想，其中 review 门禁和隔离 worktree 是「产品工厂」能否成立的关键。

## 四、评估总论

```
工作台（AionCore） = 成熟的「多 Agent 工作台引擎」（机制层满分，知识层空白）
        ↓ 补知识
blueprint + starter-kit = 「产品开发的手艺」（7 层架构 + 6 阶段质检），做成 skill 注入
        ↓ 补机制短板
multica = 「生产级开发的 4 个设计」（review 门禁 + 隔离 + 准入 + 用量）
        ↓ 结果
产品工厂 = 引擎（已有）+ 手艺（blueprint/starter-kit）+ 生产级短板（multica 思想）
```

**最终结论：三样都要，但「要法」不同——**
- blueprint / starter-kit：**要的是它们的内容（知识），不是重写它们的代码；做成 skill 即可，量级是「几份 markdown」，不是「一个子系统」。**
- multica：**要的是它的 4 个设计思想（review 门禁 / 隔离 / 准入 / 用量），去补工作台现有的 4 个短板，不是引入它的代码。**
- 工作台：**是底座，机制层不需要动，只在 TaskStatus 加一个 InReview 状态 + 每任务隔离目录，其余靠 skill 知识。**
