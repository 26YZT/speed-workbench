## 1. 改动一：Review 门禁（TaskStatus 增加 InReview）

### 1.1 目标
Agent 完成任务后，任务进入「待验收（in_review）」状态，**由人确认后才变为 completed**。这是产品工厂「防糊弄」的核心。

### 1.2 现状证据
- 枚举定义：`aionui-team/src/types.rs:228` `pub enum TaskStatus { Pending, InProgress, Completed, Deleted }`
- `Display`（`types.rs:235`）、`parse`（`types.rs:246`）
- 依赖解锁在 `Completed` 时触发：`task_board.rs:120` `if update.status == Some(TaskStatus::Completed) { self.check_unblocks(...) }`
- DB CHECK 约束：`001_initial_schema.sql:530` `CHECK (status IN ('pending','in_progress','completed','deleted'))`
- 序列化自动适配：`activity_mapping.rs:53` `status: task.status.to_string()`

### 1.3 改动清单

| # | 文件 | 改动 |
|---|---|---|
| 1 | `aionui-team/src/types.rs` | 枚举加 `InReview`（`#[serde(rename="in_review")]`）；`Display` 输出 `"in_review"`；`parse` 接受 `"in_review"`；补对应单测 |
| 2 | `aionui-team/src/task_board.rs` | **保持** `check_unblocks` 仅在 `Completed` 触发（InReview 不解锁依赖，人验收通过后才解锁） |
| 3 | 新增 `aionui-db/migrations/044_task_review_status.sql` | 用 SQLite 兼容语法重建 CHECK 约束，允许 `in_review`（先读现有 migration 编号，取下一个未用编号） |
| 4 | 前端看板 | `AionUi/packages/desktop/src/renderer/pages/team/activity/`（TaskCard / ActivityBoardLayout / activityTypes）加 `in_review` 状态列与样式；i18n 加文案 |

### 1.4 影响面（确认无需改）
- `activity_mapping.rs` 用 `to_string()` 自动序列化，无需改。
- `lib.rs` re-export `TaskStatus` 已含，无需改。
- 前端 `TaskStatus` 类型定义需同步（若前端有独立枚举，读 `activityTypes.ts` 确认）。

### 1.5 验证
```bash
cd AionCore
cargo check
cargo test -p aionui-team
cargo test -p aionui-db          # migration 测试
# 前端
cd ../AionUi && node_modules/.bin/tsc --noEmit && bun run test
```

### 1.6 验收（三栏审核）
- 完整性：枚举/DB/前端三处同步，单测过，未破坏 completed 的依赖解锁。
- 可用性：手动创建一个任务，置 in_review，前端看板显示「待验收」，确认后才 completed。
- 成本：本改动无 AI 调用（纯状态机），成本为 0。

## 6. 开发顺序与三栏审核

**顺序**：改动四（skill，纯内容，先让 Agent 有「脑子」）→ 改动一（review 门禁）→ 改动二（隔离）→ 改动三（用量）。每个改动独立提交、独立验证、独立过三栏审核。

**三栏审核**（每个改动完成时提交，任一栏不过不得进入下一个改动）：
1. **技术实现完整性**：功能点全实现、边界/错误处理覆盖、单测过、未破坏既有功能。
2. **功能可用性**：端到端真实走通、数据重启可恢复、能手动验证。
3. **AI 调用成本控制**：改动自身消耗的 AI 调用 ≤ 预算（改动一/二/四为 0，改动三自举计入），无冗余调用。
