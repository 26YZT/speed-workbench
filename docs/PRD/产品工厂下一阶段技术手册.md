# 产品工厂基础流程技术手册

> 本文档原名为“产品工厂下一阶段技术手册”，最初只覆盖访谈和蓝图。
> 当前代码已推进到最小 Team 创建、真实首任务执行、人工 Review 和测试样品验收；连续任务交付仍属于后续阶段。

## 适用范围

本手册用于产品工厂从运行详情到最小 Team 交接的基础流程：

```text
运行详情 → 需求访谈 → 蓝图审阅 → 任务草稿 → 只读交接预览 → 用户确认交接 → 现有 Team 任务图
```

只读预览不创建 Team 或修改运行状态；只有用户明确确认且后端再次校验通过，才创建一个 Team 并进入 `handed_off`。本阶段不包含 Agent 执行、发送开发消息、第二套看板、自动部署、真实模型效果评估和视觉换肤。

## 用户流程

```text
产品工厂首页
  → 打开 /product-factory/:runId
  → 补充需求访谈
  → 保存访谈草稿
  → 确认需求摘要
  → 查看并修改蓝图
  → 保存蓝图
  → 确认蓝图
  → 显式生成任务草稿
  → 编辑并保存任务草稿
  → 确认任务清单（先保存最新编辑，再用返回的 revision 确认）
  → 打开 Team 交接预览
  → 重新检查或返回任务审阅
  → 选择现有可用的 Team 助手，沿用助手配置和已有模型解析逻辑，指定一名 Leader
  → 用户明确确认交接
  → 回读已创建 Team 的 ID 和任务图（不自动进入 Team 页面）
```

## 状态规则

```text
draft
  → interviewing
  → blueprint_generating
  → blueprint_ready
  → task_draft_ready
  → handed_off（只允许由成功的后端交接写入）
```

- 保存访谈：`draft` 自动进入 `interviewing`；重复保存保持当前阶段。
- 确认访谈：必须存在非空摘要，服务端生成可编辑的蓝图草案并进入 `blueprint_ready`。
- 保存蓝图：只能在 `blueprint_generating` 或 `blueprint_ready` 阶段执行。
- 确认蓝图：只能在 `blueprint_ready` 阶段执行，并把 `confirmed` 写入蓝图 JSON。
- 生成任务草稿：要求已确认蓝图；已有合法草稿时回读，不重复生成；生成后进入 `task_draft_ready`。
- 保存任务草稿：只允许编辑未确认草稿，必须提交当前 `expected_revision`；保存成功 revision 加一。条件更新保护并发写入，保存失败时前端保留本地编辑且不继续确认。
- 确认任务草稿：校验任务完整性、唯一 ID 和依赖图，写入 `confirmed=true`，仍停留在 `task_draft_ready`；确认本身不创建 Team、不启动开发。
- 交接预览：回读服务端快照并比较 revision 和内容，复用文件元数据接口检查工作区；不修改运行状态或任务草稿。
- 正式交接：后端按 owner 重新加载最新快照，检查已确认、来源、revision、完整性、依赖、工作区与重复交接；预配成员会话后，以同一数据库事务写入 Team、`pending` 任务图、可选预算和运行绑定。普通失败补偿清理本次预配的会话，数据库回滚保持未交接。
- 重试：`run_id + task_draft revision` 映射稳定 Team / Team task ID；相同版本返回已提交的结果，旧版本返回冲突。通用 `/status` 路由不能直接声明 `handed_off`、`running`、`in_review` 或 `completed`。
- 多用户认证模式中的写操作经过登录、owner 隔离和 CSRF 校验；当前本地 WebUI Demo 的后端使用 local identity（`auth=disabled`），不能把本地页面验证冒称为远程认证验证。新交接接口的认证和 CSRF 路径由独立应用集成测试覆盖。

## API 契约

```text
GET  /api/product-factory/runs/:id
PUT  /api/product-factory/runs/:id/interview
POST /api/product-factory/runs/:id/interview/confirm
PUT  /api/product-factory/runs/:id/blueprint
POST /api/product-factory/runs/:id/blueprint/confirm
POST /api/product-factory/runs/:id/task-draft/generate
PUT  /api/product-factory/runs/:id/task-draft
POST /api/product-factory/runs/:id/task-draft/confirm
POST /api/product-factory/runs/:id/handoff
POST /api/fs/metadata  # 交接预览复用的只读文件元数据接口
```

请求体：

```json
{"interview": {"version": 1, "questions": [], "summary": "..."}}
{"blueprint": {"version": 1, "sections": [], "risks": [], "open_questions": []}}
{"expected_revision": 1, "tasks": []}
{"expected_revision": 2}
{"expected_revision": 2, "agents": [{"name": "Leader", "role": "lead", "assistant_id": "<现有助手 ID>", "model": "<现有模型 ID>"}]}
```

响应继续使用现有 `ApiResponse<T>` 包装，不新增第二套错误格式。交接响应 `data` 包含更新后的 `run`、真实 `team_id` 和草稿 ID 到 Team task ID 的 `task_id_map`；revision 冲突为 409，普通配置或预配失败不可伪装成交接成功。

## 数据契约

访谈：版本号、最多五个问题、回答/不确定状态、摘要、确认状态和更新时间。

## 已实现的最小交接与后续边界

已实现“用户确认交接 → 创建一个 Team 和任务图 → 回读 Team 信息”，包含 owner/CSRF 校验、revision 冲突、重复点击幂等与普通失败恢复；未加入并行 Agent、Git worktree 生命周期、成本报告或部署。

已有 Team Review、任务目录隔离、用量聚合和预算保护应复用，不重复开发。由于 `create_team` 会预配成员会话，数据库事务只覆盖 Team、任务图、预算和 run 绑定；会话创建在事务外。单次请求失败会尝试清理并保留可重试状态，进程在预配期间崩溃仍可能留下孤立会话，需要后续清理策略。`handed_off` Team 不参与服务器启动时自动恢复成员会话；进入现有 Team 页面会沿用该页面的初始化行为，用户应阅读提示后再主动进入。

**后续执行阶段**：真实 Agent 派工、任务 `in_progress → in_review → 人工验收`、集成失败恢复、代码隔离与部署仍需单独设计及真实环境验证。不能从当前一次 Team 创建推断这些能力已经验收。

## 首任务显式派发增量（2026-10-03）

本增量接通已有 Team 的用户消息入口，不另建执行引擎、任务看板或并行编排。代码入口已具备调用配置好的 Team 运行时的能力；本轮自动化测试替换了外部 Agent 执行，不能据此宣称真实模型开发已经成功，也不代表 L2 MVP 完成。

### 使用与契约

交接后显示“开始首个开发任务”。打开页面、刷新页面、读取执行记录均不会发起开发。用户确认可能产生模型费用及修改指定目录后，后端重新检查：

- 当前 owner、已确认任务 revision、已提交交接及已确认蓝图。
- Team 仍使用原工作区，且只配置一名 Leader；目录存在不等于安全沙箱。
- 首个无依赖任务仍为未分配的 `pending`，描述及验收标准与确认快照一致。
- 现有 Team 的记录预算未耗尽、没有活跃工作；检查异常时此入口拒绝准入。
- 执行 brief 不超过 32 KiB。brief 包含产品想法、蓝图、首任务及验收标准，要求只完成此任务并提交人工 Review，不自我批准。

| 接口 | 行为 |
|---|---|
| `GET /api/product-factory/runs/{id}/execution` | owner 隔离的只读回执；无记录时 `data.execution=null` |
| `POST /api/product-factory/runs/{id}/start` | `expected_revision` 必填；经认证和 CSRF 校验，原子保留唯一派发尝试，再调用现有 Team 消息入口 |

`048_product_factory_execution.sql` 保存回执，唯一键为 run ID。预留时对 run、Team、首任务快照做条件检查。并发客户端、独立服务实例及响应丢失后的重复请求都回读已有记录，不重复投递。

### 状态与恢复边界

- `pending`：已保留尝试，但派发结果未确认。
- `enqueued`：Team 返回信箱 message ID 与 Team run ID；只证明投递被接收，不证明 Agent 已运行。
- `uncertain`：投递报错或回执不完整。消息可能已写入，禁止自动重发。

产品整体状态仍保持 `handed_off`，不会仅凭投递回执改为 `running` 或 `completed`。实际成员状态、日志与人工 Review 沿用 Team 页面。应用重启只允许有 `enqueued` 回执的交接 Team 进入原有恢复流程；`pending`/`uncertain` 不自动启动成员。

进程在预留后崩溃，或消息成功后保存回执失败，可能留下 `pending`。本增量优先避免重复费用，不承诺恰好执行一次，也未实现自动恢复；用户需先检查 Team。不要删除回执或改数据库来重试。

2. 首轮派发已在真实冒烟中验证：任务分配、canonical assignment notice、task ID 绑定、任务工作区准备和该 task 的 token usage 归属均成立；`cost_est` 仍为空，不能宣称每个工位成本金额已完整记账。

4. 完整安全沙箱、代码集成隔离、可运行产物启动/关闭/重开、数据持久化与交付证据包。

- Team：`factory-01a10077-fe21-7f21-8ae3-6676e68034f2-r1`。
- Agent：隔离库中的 `bare:8e1acf31` / Codex CLI。
- 首任务：`data-1`，真实状态从 `pending` 变为 `in_progress`，再进入 `in_review`。

- 人工 Review 前检查：Node round-trip 持久化/重新读取通过；非法标题数量校验通过；不支持的文档版本被拒绝。任务没有自动批准。

这次冒烟证明了 **真实 Agent 可被派发、可使用任务工作区、可写入产物、可提交 `in_review`、任务用量可归属**。它还没有证明最终产品可运行，也没有证明成本金额、后续任务编排和最终交付闭环。

### 冒烟暴露的问题

1. Agent 提交 `in_review` 后，Team 仍保留了一个后台 follow-up 队列；随后 Codex 尝试再次调用，出现 `default` 模型 503。下一步需要让任务进入 `in_review` 后阻止同一任务的无必要后台续跑，避免额外调用。
2. 当前 Codex 助手的默认模型是 `default`，真实上游返回“当前 default 模型暂不可用”；生产流程不能依赖未明确解析的 `default` 模型，应在派发前显示并确认实际模型。
3. usage ledger 已记录 token，但 `cost_est` 仍为空，预算余额未随本次真实调用减少；成本验收仍未通过。
4. Codex 的部分外部 MCP（Notion、computer-use、插件远程同步）在隔离环境不可用，但未阻止本次首任务完成；后续需要明确 Agent 工具降级和失败边界。

隔离冒烟实例已停止，未修改正式 AionUi 开发数据库，也未自动批准 Review。

### 2026-10-03 修复进展

- Team 会话层现在拒绝 Agent 向自身发送 Agent 消息：在写 mailbox、申请 enqueue lease 或唤醒 runtime 之前返回错误，避免任务进入 `in_review` 后因自发消息产生无意义 follow-up。
- 前端 Team 模型解析器不再为无明确模型的 ACP 助手发送字符串 `default`；改为空模型，让对应 ACP runtime 使用自己的默认模型。Codex 的真实冒烟日志已证明字符串 `default` 会触发上游 503，因此不能作为通用模型 ID。
- 新增/更新回归测试：自发消息不创建 mailbox 或后台工作；ACP 无模型时返回空模型。真实模型尚未重复调用验证第二项，避免在成本未闭环时再次产生费用。
- 新增成本未知保护：只要配置了 Team 预算，而历史 usage 存在 token 但没有可信 cost_est，执行入口拒绝继续派发，并返回“成本无法核验”，不会把未知成本当作 0 元。Team event loop 也会暂停新 turn。没有配置预算时可以继续运行，但汇总会标记 cost_unknown=true。
- 当前仍没有通用模型价格表；Codex 的真实 usage 可能只提供 token、不提供美元金额。因此这一步是“安全地拒绝不确定预算”，不是“已经准确算出费用”。
## 模型成本配置（2026-10-03）

usage 事件如果已经携带美元金额，系统优先使用运行时金额；如果只有 token，则可读取数据目录下的 `model-pricing.json`（也可用环境变量 `AIONUI_MODEL_PRICING_FILE` 指定路径）进行估算。文件不存在时保持成本未知，不会假装是 0 元。

格式：

```json
{
  "version": 1,
  "models": {
    "your-model-id": {
      "input_usd_per_million": 0.0,
      "output_usd_per_million": 0.0,
      "cached_read_usd_per_million": 0.0,
      "cached_write_usd_per_million": 0.0,
      "input_includes_cached_tokens": false
    }
  }
}
```

价格必须由用户根据实际模型/供应商账单配置，不能使用未经核验的示例价格。带缓存 token 但没有对应缓存价格时，估算仍标记为未知。

当前成本策略：

- 运行时提供金额：记录该金额。
- 配置价格表可估算：记录估算金额。
- 两者都没有：`cost_unknown=true`；配置预算时阻止新的 Agent turn。

`input_includes_cached_tokens` 对 Codex 这类把缓存 token 包含在 `input_tokens` 中的后端应设为 true；否则保持 false。

当前新增交付检查接口：

GET /api/product-factory/runs/{id}/delivery

该接口只读计算运行完成、任务是否全部完成、工作区是否可用和成本状态，并返回任务级与累计用量摘要；它不会自动启动 Agent、合并代码或部署产品。

正式成本报告接口：

GET /api/product-factory/runs/{id}/cost-report

该接口返回 Product Factory run、任务状态统计、Team 累计 Token、每任务成本和生成时间；它不会重新调用模型，也不会产生费用。
