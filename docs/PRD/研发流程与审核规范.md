# 研发流程与审核规范

> 本文档定义产品工厂从开发到迭代的完整流程，以及每个阶段的三项审核标准。
> 适用于：产品工厂自身的开发，以及后续每一次功能迭代。

---

## 一、研发流程（八步闭环）

```
① PRD 撰写 → ② 需求对齐 → ③ 分阶段开发 → ④ 后端/前端实现
      ↑                                                    ↓
      ⑧ 用户反馈迭代 ← ⑦ 上线 ← ⑥ 测试 ← ⑤ 前后端联调
```

迭代时，⑧ 回到 ①：为新功能写「新版 PRD」，再走一遍 ②~⑦。

### 各步骤定义

| 步骤 | 做什么 | 谁主导 | 产出 |
|---|---|---|---|
| ① PRD 撰写 | 把想法写成结构化需求（六维度 + 五要素 + 功能清单 + 验收标准） | AI 产品经理 | PRD 文档 |
| ② 需求对齐 | 逐条确认范围/成本/边界/验收，答不上来的标「待确认」 | 产品经理 + 用户 | 决策台账（≤10 项） |
| ③ 分阶段开发 | 把 PRD 拆成阶段里程碑，每阶段定义产出与验收 | AI 产品经理 + 开发 AI | 阶段计划 |
| ④ 后端/前端实现 | 按阶段写代码，改完必跑验证 | 开发 AI | 代码 + 单测 |
| ⑤ 前后端联调 | 前端调后端接口全链路走通 | 开发 AI | 联调记录 |
| ⑥ 测试 | 单测 + 真实模型冒烟 + 边界/安全测试 + 成本压测 | 开发 AI + 用户验收 | 测试报告 |
| ⑦ 上线 | 打包/部署 + 上线验收 | 开发 AI + 用户 | 安装包 + 验收记录 |
| ⑧ 用户反馈迭代 | 收集反馈 → 写新版 PRD → 循环 | 产品经理 | 新版 PRD |

---

## 二、三项审核核心（每个阶段都必须过）

> 每个阶段结束时，开发 AI 必须提交「三栏审核表」，任一栏不通过不得宣布阶段完成。

### 审核 1：技术实现完整性

**定义**：功能是否按 PRD 完整实现，无偷工减料、无隐藏 bug、无破坏既有功能。

| # | 检查项 |
|---|---|
| 1.1 | 本阶段范围内功能点**全部实现**，没有提前做后续阶段（越界也算不完整） |
| 1.2 | 边界情况与错误处理已覆盖（空输入/超时/失败/越权） |
| 1.3 | 遵循代码规范（前端 Arco 组件/i18n；后端分层/禁止凭名字猜行为） |
| 1.4 | 单测已运行且通过（写通过数/总数） |
| 1.5 | 类型检查 / lint / 编译通过 |
| 1.6 | 未破坏既有功能（回归测试通过） |
| 1.7 | 关键逻辑有代码注释/文档说明 |

### 审核 2：功能可用性

**定义**：目标用户能不能**真的**用它完成核心任务，而非「演示能看」。

| # | 检查项 |
|---|---|
| 2.1 | 端到端核心链路真实走通（不是 mock 假装走通） |
| 2.2 | 真实模型冒烟已运行（无 Key 时写「待验」，**不得写「是」**） |
| 2.3 | 数据在服务重启后可恢复，已实际验证 |
| 2.4 | 用户能自己打开验证（可访问地址 / 「照着点」步骤） |
| 2.5 | 桌面与移动端宽度已检查（有界面时） |
| 2.6 | 错误提示对用户友好，不泄露技术堆栈/密钥 |
| 2.7 | 用户验收清单逐项通过 |

### 审核 3：AI 调用成本控制

**定义**：达成功能的同时，AI 调用成本在预算内、且没有浪费。

| # | 检查项 |
|---|---|
| 3.1 | 本阶段 AI 调用成本 ≤ 预算上限（上限在需求对齐阶段确定，暂不定死） |
| 3.2 | 简单环节用低价模型，关键环节才用强模型（模型分级使用） |
| 3.3 | 无 Key 时用 mock 推进，标注「待验」，不烧真实调用 |
| 3.4 | 无重复/冗余调用（同样的活不调两次；结果可缓存则缓存） |
| 3.5 | 有预算护栏：超限自动停止并报告，而非无限烧钱 |
| 3.6 | 每任务的 token / 成本已记录并聚合，可追溯 |
| 3.7 | 上下文管理：长任务不无限膨胀（该压缩/该分块要处理） |

## 三、三栏审核表模板（每阶段结束提交）

```markdown
## 阶段 N 审核表

### 审核 1：技术实现完整性
- [ ] 1.1 功能点全部实现
- [ ] 1.2 边界/错误处理覆盖
- [ ] 1.3 代码规范
- [ ] 1.4 单测通过（_/___）
- [ ] 1.5 类型检查/lint/编译通过
- [ ] 1.6 未破坏既有功能
- [ ] 1.7 注释/文档

### 审核 2：功能可用性
- [ ] 2.1 端到端走通
- [ ] 2.2 真实模型冒烟（或「待验」）
- [ ] 2.3 数据重启可恢复
- [ ] 2.4 用户可自行验证
- [ ] 2.5 多端宽度检查
- [ ] 2.6 错误提示友好
- [ ] 2.7 验收清单通过

### 审核 3：AI 调用成本控制
- [ ] 3.1 成本 ≤ 预算
- [ ] 3.2 模型分级
- [ ] 3.3 mock 推进标注待验
- [ ] 3.4 无冗余调用
- [ ] 3.5 预算护栏生效
- [ ] 3.6 用量已记录
- [ ] 3.7 上下文受控
```

**通过标准**：三栏均无「未勾选」。有未勾选项，必须写明原因和补救计划，经确认后才可继续下一阶段。

## 四、阶段与审核的对应关系

| 阶段 | 三项审核的侧重点 |
|---|---|
| 0 需求对齐 | 完整性（范围无遗漏）、可用性（验收标准可度量）、成本（预算明确） |
| 1 文档清理 | 完整性（文档与现状一致） |
| 2 后端门禁/隔离/用量 | 完整性（后端逻辑）、成本（用量表落地） |
| 3 知识注入（skill） | 完整性（规则完整）、可用性（skill 能被正确加载执行） |
| 4 前端界面 | 可用性（页面真实可用）、完整性（i18n/组件规范） |
| 5 联调 | 可用性（全链路真实走通） |
| 6 测试 | 三项全查（含成本压测） |
| 7 上线 | 三项全查（含上线后成本验证） |
| 8 迭代 | 回到新版 PRD，重新走流程 |

## 五、与既有规则卡的关系

本规范**补充**而非替代上游规则卡：
- `AionUi/AGENTS.md`（前端编码规范）→ 审核 1.3 的依据；
- `AionCore/AGENTS.md`（后端规则 + 禁止凭名字猜行为）→ 审核 1.3 的依据；
- ai-product-starter-kit 的「10 项是否表 + 证据包」→ 审核 2 的细化来源；
- 本规范的「三项审核」是**每阶段的门槛**，starter-kit 是否表是**功能内的质检**，两者是「阶段级」与「任务级」的嵌套关系。
