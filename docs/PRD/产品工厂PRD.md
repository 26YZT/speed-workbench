## 1. 产品概述

### 1.1 背景与问题

用户（产品经理 / 非技术创业者）有一个产品想法，但面临三重门槛：

1. **不会写代码**，无法把想法变成能演示的原型；
2. **交给单个 AI**，质量不可控、上下文易爆、易糊弄；
3. **交给多个 AI**，没有统一调度、验收和成本控制。

现有底座「Speed Workbench」已是一台成熟的**多 Agent 工作台引擎**（团队看板、任务调度、邮箱、MCP、技能、多后端运行时），但它缺「产品开发」这门**领域手艺**：没有「想法→架构」的推导规则，没有「分阶段开发→验收」的质检标准，没有「产出需人验收」的 review 门禁。

### 1.2 产品定位（一句话）

**输入一句产品想法，自动产出可运行、可验收、可迭代的 AI 产品原型。**

### 1.3 目标用户

| 用户                | 场景                        | 人机比            |
| ------------------- | --------------------------- | ----------------- |
| 非技术产品经理      | 有想法，要快速验证产品原型  | 1 人配 N 个 Agent |
| 独立开发者 / 创业者 | 快速产出 MVP 去融资/验证    | 同上              |
| 技术负责人          | 用多 Agent 并行开发大型项目 | 1 人监督 M 个团队 |

### 1.4 核心价值

1. **快**：一句话想法 → 可运行原型，全流程自动化；
2. **稳**：每个阶段过「质量闸门」，产出可验收、防糊弄；
3. **省**：AI 调用成本有预算护栏，简单活不烧贵模型；
4. **可复现**：流程是固化 SOP，不是一次性的 prompt 魔法。

### 1.5 成功标准（北极星）

- 一个「一句话想法」在 **30 分钟内**产出可打开的原型；
- 原型通过全部阶段闸门（测试过、Key 未泄露、数据重启不丢）；
- 单次生成成本 **≤ 预算上限**（上限在「需求对齐」阶段确定，暂不定死，见 3.4）；
- 用户对产出的「可用性」评分 ≥ 4/5。

## 2. 竞品与差异化

调研对象：MetaGPT（7w⭐）、OpenHands（8.9w⭐）、bolt.new、Lovable、v0、ChatDev（3.4w⭐）、gpt-engineer（5.5w⭐）、aider、claude-task-master、multica。

| 竞品                    | 强项                     | 我们的差异化                                                             |
| ----------------------- | ------------------------ | ------------------------------------------------------------------------ |
| bolt.new / v0 / Lovable | prompt→全栈 app 一键部署 | 它们只做「单 App 生成」，我们是**桌面工作台 + 多 Agent 团队 + 可审可改** |
| MetaGPT / ChatDev       | 角色分工 SOP             | 它们偏研究/脚本，我们是**可用的桌面产品 + 看板 + 调度**                  |
| OpenHands / multica     | 多 Agent 运行时          | 我们**本地桌面、自带多 Agent 团队看板、自带质检门禁**                    |

**护城河**：把「产品工厂流水线」做成**可复用、可迭代的本地 skill**，不锁定任何模型/厂商。

## 3. 需求拆解

### 3.1 需求硬事实（六维度）

| 维度     | 结论                                                                                |
| -------- | ----------------------------------------------------------------------------------- |
| 目标     | 一句话想法 → 可运行 AI 产品原型；成功标准见 1.5                                     |
| 用户     | 非技术产品经理为主；异步交互为主（派单→开发→验收），聊天准同步                      |
| 核心闭环 | 想法输入 → 蓝图推导 → 拆任务卡 → 看板派单 → 多 Agent 并行开发 → 质检闸门 → 拼装交付 |
| 交付物   | 可运行原型 + 源码 + 证据包（截图/可打开地址/是否表）+ 成本报告                      |
| 边界     | 原型默认不自动上线；付费云资源创建前必须人工确认；Agent 产出必须过人 review         |
| 约束     | 单次生成成本上限；多 Agent 隔离不冲突；密钥不进仓库；数据持久化                     |

### 3.2 五要素映射

| 要素 | 落点                                                                                      |
| ---- | ----------------------------------------------------------------------------------------- |
| 工具 | 复用 AionCore：Agent 后端（Claude Code/Codex/ACP）+ MCP + 文件/Shell/git                  |
| 知识 | 新增两个 skill：`product-blueprint`（7 层架构+17 组件规则）、`product-sop`（6 阶段+闸门） |
| 观察 | 复用实时事件流 + 执行日志 + 用量追踪（新增）                                              |
| 行动 | 复用 `aionui-session` BackendAdapter spawn 外部 CLI；看板派单                             |
| 权限 | 复用团队治理（Lead-only 工具）+ 新增 review 门禁（人确认才 close）                        |

### 3.3 功能清单（七工位流水线）

> 每个工位 = 一个可独立验收的功能模块。

**工位 ① 想法输入**

- F1.1 聊天式输入一句话想法（复用现有对话界面）
- F1.2 访谈式补全：每轮 ≤5 个问题、每个附示例、可答「不确定/按推荐」（复用 starter-kit 思想）
- F1.3 输出 PRD 草稿，人工确认

**工位 ② 蓝图推导（新增 skill `product-blueprint`）**

- F2.1 需求拆解（目标/用户/闭环/交付物/边界/约束）
- F2.2 五要素映射（工具/知识/观察/行动/权限）
- F2.3 组件选型（17 组件决策映射表，只选需要的）
- F2.4 产出七层架构方案 + 工具清单 + 技术栈选型

**工位 ③ 拆解工位（新增 skill `product-sop`）**

- F3.1 按 6 阶段（PRD体检→技术适配→后端MVP→正式前端→上线→收尾）拆模块
- F3.2 生成「模块任务卡」：后端/前端/DB/测试/部署，带依赖（blocked_by）
- F3.3 每张卡标注验收标准 + 闸门检查项

**工位 ④ 看板派单（复用 `aionui-team` task_board）**

- F4.1 任务卡进看板（状态列 + 依赖 + owner 认领）
- F4.2 多 Agent 并行认领（复用 work_coordinator slot 状态机）
- F4.3 实时事件推送（复用 realtime）

**工位 ⑤ 并行开发（复用 + 新增隔离）**

- F5.1 每任务独立隔离目录（新增，参考 multica worktree）
- F5.2 spawn 外部 Agent CLI 开发（复用 aionui-session BackendAdapter）
- F5.3 执行日志/进度回传（复用实时事件流）
- F5.4 中途插话/取消/重试（复用）

**工位 ⑥ 质检闸门（新增）**

- F6.1 `TaskStatus` 增加 `InReview`（产出落「待验收」列，不自动 Completed）
- F6.2 每张卡过「10 项是否表」（测试过？Key 泄？重启丢？…）
- F6.3 证据包落盘（截图 + 可打开地址 + 是否表）

**工位 ⑦ 交付（复用 + 新增）**

- F7.1 拼装可运行原型（复用 office/file/skill-runtime 组装）
- F7.2 成本报告（新增：每任务 token/成本聚合）
- F7.3 一键本地运行 / 部署指引（复用 + starter-kit 部署手册）

### 3.4 非功能需求

| 类       | 需求                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 成本控制 | 单次「想法→原型」总成本 ≤ 预算上限（**待定**，需求对齐阶段确定）；简单环节用低价模型，关键环节才用强模型；无 Key 时用 mock 推进并标「待验」 |
| 安全     | 密钥不进仓库/前端/日志；权限判断在后端；沙箱隔离                                                                                            |
| 可观测   | 每任务日志 + 用量 + 状态实时可见                                                                                                            |
| 可恢复   | 任务/会话/看板数据持久化 SQLite，重启不丢                                                                                                   |
| 兼容     | 保留 AionUi/AionCore 上游归属声明；技术标识符不改                                                                                           |

## 5. 分阶段开发计划

> 遵循研发流程：PRD 撰写 → 需求对齐 → 分阶段开发 → 前后端实现 → 联调 → 测试 → 上线 → 迭代。每阶段过三项审核（详见《研发流程与审核规范》）。

| 阶段                   | 内容                                              | 主要产出             | 审核重点     |
| ---------------------- | ------------------------------------------------- | -------------------- | ------------ |
| 0 需求对齐             | 评审本 PRD，确认范围/成本/边界                    | 决策台账（≤10 项）   | 三项目标对齐 |
| 1 文档与品牌清理       | 更新 README/AUTHORS/打包说明；归档 codex-开发说明 | 清理后的文档         | 完整性       |
| 2 后端：门禁+隔离+用量 | TaskStatus.InReview + 隔离目录 + 用量表           | Rust 后端改动 + 测试 | 完整性/成本  |
| 3 后端：知识注入       | 新增 product-blueprint / product-sop 两个 skill   | skill 资产           | 完整性       |
| 4 前端：产品工厂界面   | 想法输入页 + 流水线看板 + 质检/交付页             | 前端页面 + 测试      | 可用性       |
| 5 联调                 | 前端↔后端全链路走通                               | 联调记录             | 可用性       |
| 6 测试                 | 单测 + 真实模型冒烟 + 成本压测                    | 测试报告             | 三项全查     |
| 7 上线                 | 打包桌面端 + 部署说明                             | 安装包 + 文档        | 三项全查     |
| 8+ 反馈迭代            | 按用户反馈从新版 PRD 开始循环                     | 新版 PRD             | 循环         |

### 当前实现位置（2026-10-02）

当前工作台已完成以下可验证产品阶段：

```text
产品想法 → 需求访谈 → 蓝图审阅 → 任务草稿生成/编辑/确认 → 只读交接预览 → 明确确认后创建 Team 与待执行任务图
```

交接预览仍是只读规则检查；只有用户选择成员并明确确认交接时，后端才原子提交 Team、待执行任务图、预算与运行绑定。交接会预配成员会话记录，但不会自动导航到 Team 页面或启动成员运行时；打开现有 Team 页面会触发它自身的会话运行时初始化，因此页面明确提示后交由用户决定。

2026-10-02 在已登录 Demo 中分别验收了两条路径：原有运行缺少工作区路径时明确拒绝，运行记录与任务草稿不变；新建的 `Handoff QA 2026-10-02` 从想法、访谈、蓝图编辑、任务编辑/确认走到有效工作区交接，得到 1 个 Team 和 4 条 `pending` 任务。相同 revision 再提交返回原 Team，旧 revision 返回 409；刷新页面后交接结果仍可回读。该 Team 的成员消息和 mailbox 均为 0，工作区未生成 `.tasks` 目录。本验收不代表 Agent 实际开发、代码隔离或交付完成。

现有 Team 人工 Review 门禁、任务目录隔离、用量/成本聚合与预算保护已有实现，后续应复用并以真实 Agent 联调，不按旧任务书重复开发。任务目录隔离不等于完整 Git worktree 生命周期或安全沙箱；真实 Agent 执行、并行开发、完整代码隔离与集成交付、成本报告和部署仍需后续阶段验证。交接时预配的成员会话位于数据库事务之外：普通失败会尝试清理，进程在预配中崩溃仍可能留下未绑定的会话记录，不能宣称所有外部副作用完全原子。

## 6. 整体验收标准

### MVP 执行增量说明（2026-10-03）

首版先争取 L2：从想法到经过质检、可本地运行和重开的产品；复杂产品的通用架构生成属于后续迭代。本轮新增“交接后显式派发首个无依赖任务”的最小入口，仅支持一名 Team Leader，复用 Team，不默认并行或自动部署。Harness 仅在交付产品涉及 Agent 时按需加入，不是每个原型的必选组件。

新增入口有持久化一次性派发回执、版本/快照检查和预算准入检查，但真实 Agent 执行及产品交付仍未验收；普通用户消息的首轮成本归属、预算异常放行、失败恢复、后续任务推进和本地交付仍是 L2 之前的待办。不可把 `enqueued` 回执当成运行或完成证明。细节见《产品工厂基础流程技术手册》的“首任务显式派发增量”。

1. **可运行**：一条命令能起，配置密钥外置；
2. **可容错**：工具失败/模型幻觉/超时/越权有明确降级；
3. **可观测**：日志 + 指标 + 成本轨迹；
4. **可测试**：核心流程有单测，权限与安全有边界测试；
5. **可部署**：明确的部署形态与启动文档；
6. **可度量**：对齐 1.5 成功标准并采集。

## 7. 风险与对策

| 风险                        | 对策                                              |
| --------------------------- | ------------------------------------------------- |
| 多 Agent 并行改同一文件冲突 | 阶段 2 的隔离工作区（每任务独立目录，交付时合并） |
| AI 产出无法验收             | 阶段 2 的 review 门禁 + 阶段 3 的闸门是否表       |
| 成本失控                    | 阶段 2 的用量追踪 + 预算护栏（超限自动停）        |
| 上游更新覆盖定制            | `UPSTREAM_UPDATE_ENABLED=false` 已设，保持        |
| 模型能力不足                | 模型对比台（已有）选型 + 关键环节用强模型         |
