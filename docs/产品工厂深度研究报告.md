# 产品工厂深度研究报告

> 目标：把「产品经理工作台」加强成一台**可真实使用、快速产出 AI 产品原型的「产品工厂」**。
> 方法：联网调研成熟 AI 产品工程 + 逐个读源码取证（multica / ai-product-starter-kit / agent-blueprint / 工作台 AionCore）。
> 日期：2026-09-29

## 第一部分：成熟的 AI 产品工程，都有哪些功能？

调研对象（按 star 数）：OpenHands 8.9w⭐、MetaGPT 7w⭐、crewAI 5.9w⭐、gpt-engineer 5.5w⭐、aider 4.9w⭐、ChatDev 3.4w⭐、claude-task-master 2.8w⭐、bolt.new 1.6w⭐、Paca、dyad、Lovable/v0（商业）。

把它们的共性能力归纳成 **8 大类、一张功能地图**：

### A. 需求 → 方案（把模糊想法变成可落地规格）
| 能力 | 谁在做 |
|---|---|
| 一句话想法 → PRD（访谈式补全、≤5 问/轮） | starter-kit、v0 |
| 产出用户故事 / 竞品分析 / 数据结构 / API 设计 | MetaGPT |
| 架构推导 + 组件选型（7 层 + 17 组件） | agent-blueprint |
| 代码审计 → 差距报告 + 反推 PRD | agent-blueprint |

### B. 多 Agent 编排（一群 Agent 分工协作）
| 能力 | 谁在做 |
|---|---|
| 角色分工：PM / 架构师 / 工程师 / QA | MetaGPT、ChatDev 1.0 |
| 队长/队员 + 邮箱 + 任务看板 + 依赖 + 认领 | **AionCore aionui-team**、multica |
| 零代码定义 agent / workflow / task | ChatDev 2.0 |
| 动态编排（puppeteer 式学习编排） | ChatDev |

### C. 执行运行时（Agent 真正在哪干活）
| 能力 | 谁在做 |
|---|---|
| 多种 Agent 后端：Claude Code / Codex / OpenHands / ACP 协议 | OpenHands、multica、**AionCore aionui-session** |
| 多后端：本地 / Docker / VM / 云端 | OpenHands |
| 隔离工作区 / worktree / 沙箱 | multica |
| 自带 Key / 自带模型（不锁定厂商） | dyad、OpenHands、**AionCore** |

### D. 项目管理 / 看板
| 能力 | 谁在做 |
|---|---|
| 任务看板（状态列 + 依赖 + 认领 owner） | multica、**AionCore task_board**、Paca |
| 自动把 GitHub issue 拆成任务 | OpenHands |
| review 门禁（产出不自动进 main） | multica |
| 中途插话 / 取消 / 重试 | multica、aider |

### E. 自动化 / 调度
| 能力 | 谁在做 |
|---|---|
| 定时任务 + 事件触发（webhook）automations | OpenHands、**AionCore aionui-cron**、multica autopilot |
| 集成 Slack / GitHub / Linear / Notion | OpenHands |
| 多渠道（Slack/微信/钉钉/飞书） | **AionCore aionui-channel**、multica |

### F. 质量 / 验收（防 AI 糊弄）
| 能力 | 谁在做 |
|---|---|
| 阶段闸门「是否表」+ 证据包 | starter-kit（独有） |
| 测试 / 类型检查 / lint 强制通过 | 各工具 |
| 成本 / 用量追踪 | multica |

### G. 部署 / 交付
| 能力 | 谁在做 |
|---|---|
| prompt → 全栈 app 一键部署 | bolt.new、v0、Lovable |
| 本地跑 + 云端部署双模式 | dyad、OpenHands |
| git / PR / 分支交付 | multica |

### H. 协作 / 交互
| 能力 | 谁在做 |
|---|---|
| 聊天式 + 实时事件流 | 各工具、**AionCore aionui-realtime** |
| 模型对比台（同一提示词比 2~4 个模型） | 工作台 ModelBench（作者自研） |

**一句话**：成熟 AI 产品工程 = 「想法→方案」+「多 Agent 编排」+「运行时」+「看板」+「自动化」+「质量门禁」+「部署」+「协作」。你的工作台已经在 C/D/E/H 四类里有了底座，缺的是 A/B 的「产品化流水线」和 F 的「质量门禁」。

## 第二部分：产品工作台是按 blueprint + starter-kit 开发的吗？—— **不是，但它已经自带一台「multica」**

### 2.1 代码取证：它是 AionUi/AionCore 的品牌定制分支

三个铁证：

1. **`README.md` 自述**：「基于 AionUi/AionCore 定制开发，上游提供基础架构与通用能力」「会话、通用助手、团队、定时任务等基础能力来自上游，本仓库不将这些能力声明为独立原创」。
2. **`docs/MODIFICATIONS.md`**：92 个相对上游的文件，清一色是品牌名/i18n/图标/ModelBench/项目文件夹——**没有任何「6 阶段 / 闸门 / 证据包 / 7 层架构」的内容**。
3. **全仓 grep** `starter-kit / agent-blueprint / 阶段闸门 / 证据包 / 是否表 / PRD体检 / 技术适配` —— 零命中（唯一「blueprint」是 PPT 样式名 `dark--blueprint-grid`）。

**结论：工作台与 agent-blueprint、ai-product-starter-kit 无血缘关系。**

### 2.2 但更重要：上游 AionCore 已经内置了一台「multica」

逐个读 `AionCore/crates/` 源码后，发现三个 crate 合起来就是一套完整的多 Agent 开发系统：

| AionCore crate | 能力 | multica 对应物 |
|---|---|---|
| `aionui-team/src/task_board.rs` | 任务看板：`blocked_by` 依赖、`owner` 认领、状态机、`team.taskChanged` 实时广播 | issue 看板 |
| `aionui-team/src/scheduler/` | `TeammateManager`：wake、crash_recovery、dedup、agent_lifecycle | 任务队列 + 认领 |
| `aionui-team/src/work_coordinator/` | 工作协调器：`WorkPriority`（前台/控制/定向/后台）、`SlotPhase`（Idle/Queued/Starting/Running/Paused/Blocked） | dispatch 准入 |
| `aionui-team/src/mailbox.rs` | 异步邮箱（Message/IdleNotification/ShutdownRequest） | 消息/评论 |
| `aionui-team/src/mcp/` | 团队 MCP server（stdio） | MCP 插件 |
| `aionui-team/src/team_run/` | 团队运行管理 | 运行生命周期 |
| `aionui-session/src/adapter.rs` | `BackendAdapter`：「如何新增 agent」的唯一入口，FSM + `SessionEvent` | `pkg/agent` Backend 接口 |
| `aionui-ai-agent/` | `AgentRegistry` 探测、`ActiveLeaseRegistry` 租约、`RuntimeTokenService`、ACP/Antigravity/Aionrs 会话 | daemon 探测 + 租约 |
| `aionui-cron` | 定时任务 | autopilot cron |

前端 `AionUi/pages/team/` 也已经有了 `ActivityBoardLayout`（看板布局）、`TaskCard`（任务卡）、`TeamActivityView`、`TeamCreateModal`。

**所以：你想「参考 multica 的多 Agent 并行开发」——执行引擎你已经有了一台，不用从零造。**

### 2.3 工作台 vs multica 的三处差距（值得补的点）

1. **review 门禁缺失**：`TaskStatus` 只有 `Pending/InProgress/Completed/Deleted`，没有「InReview/待验收」——multica 的「产出落 review 列、人确认才算完成」这个最关键的品质保证，工作台没有。
2. **隔离工作区**：multica 的 per-task worktree / 独立 workdir，AionCore 的 `aionui-project` 有项目绑定但无「每任务隔离目录」的强制。
3. **用量/成本追踪**：multica 按 task 记录 token/成本，AionCore 未看到对应层。

## 第三部分：三者结合 ——「产品工厂」的完整设计

### 3.1 三者的分工（一句话定位）

| 项目 | 在工厂里的角色 | 提供什么 |
|---|---|---|
| 工作台 AionUi/AionCore | **车间**（底座） | 桌面容器 + 多 Agent 团队看板 + 调度 + 邮箱 + MCP + 技能 + 多后端运行时 |
| multica | **大型项目开发范式** | 任务队列 + 原子认领 + review 门禁 + 隔离 worktree + autopilot + 用量追踪 |
| starter-kit | **质检标准 + 施工 SOP** | 6 阶段 + 闸门是否表 + 证据包 + 三份手册 |
| agent-blueprint | **产品蓝图** | 五要素 + 7 层架构 + 17 组件选型 + 正向方案/反向审计 |

### 3.2 产品工厂的七工位流水线

```
① 想法输入：你说一句话 / 丢一份 PRD
② 蓝图工位：lead agent 跑 blueprint 推导 → 7 层架构 + 组件选型 + 工具清单（架构方案）
③ 拆解工位：按 starter-kit 6 阶段，把方案拆成「模块任务卡」（后端/前端/DB/测试/部署）
④ 看板派单：任务卡进 aionui-team 看板（带 blocked_by 依赖 + owner 认领）
⑤ 并行开发：多个 teammate agent 各自认领模块，在隔离目录并行写代码
⑥ 质检工位：每个模块过 starter-kit「闸门是否表」（测试过没？Key 泄没？重启丢不丢？）
⑦ 交付工位：拼装成可运行原型 + 证据包（截图 + 可打开地址 + 是否表）
```

### 3.3 落地路线（四步，务实）

**第一步：不改架构，用「技能 + 团队提示词」把流水线跑起来（1~2 周）**
- AionCore 已有 `builtin-skills/` 机制（morph-ppt、officecli-* 都是这么做的）。
- 新增一个内置 skill：`product-factory`，把「②蓝图推导（嵌入 blueprint 7 层/17 组件规则）+ ③拆解规则（嵌入 starter-kit 6 阶段）」写成 SKILL.md，lead agent 加载后按 SOP 驱动 teammate。
- 用现有 team 看板跑通一次「想法 → 原型」。

**第二步：补 review 门禁 + 质量闸门（1 周）**
- `TaskStatus` 增加 `InReview` 状态（`types.rs` 一个枚举 + 看板一列）。
- 把 starter-kit 的「10 项是否表 + 证据包」做成任务卡的验收模板，`docs/evidence/阶段N/` 落盘。

**第三步：把 starter-kit 手册 + blueprint 规则做成知识库（1~2 周）**
- 三份手册（技术栈/前端/部署）+ blueprint 决策表，做成 skill 的 reference 文件，按需加载（对应 multica 的 skill bundle 思想）。

**第四步：参考 multica 做工程化增强（按需）**
- 隔离 worktree、dispatch reason 枚举、用量追踪，增强 `aionui-team` 的隔离与可观测。

### 3.4 结论

**完全可行，且比预想的更近。** 你手上的四个项目恰好各占一环：

```
agent-blueprint（蓝图）→ starter-kit（质检 SOP）→ 工作台 AionCore（执行引擎）→ multica（范式参照）
```

产品工厂 = **用工作台的团队看板当流水线，用 blueprint 当「需求→架构」的头脑，用 starter-kit 当「每道工序的质检闸门」，用 multica 当「大型项目怎么并行开发的参照」**。

一句话：**你的工厂车间（AionCore 的多 Agent 团队 + 看板 + 调度 + MCP + 技能）已经建好了，现在缺的是「流水线设计图（blueprint）」和「质检标准（starter-kit）」这两样软的东西——而这两样恰好都是你手上现成的。**
